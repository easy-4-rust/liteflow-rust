# liteflow-rust 全量迁移路线图

> 版本：v1.0（2026-07-25）｜基线：dromara/liteflow v2.10.0（模块边界）+ v2.16.0（语义超集）

## 一、总目标

以 dromara/liteflow 为蓝本，实现能力完全对齐的 liteflow-rust workspace，目标 7 个 crate：

| crate | 对应 Java 模块 | 状态 |
|---|---|---|
| liteflow-core | liteflow-core | 🚧 进行中（结构 ~40%，语义 ~95% 主干） |
| liteflow-derive | annotation/ + 声明式组件 | ⬜ S4 |
| liteflow-rule-plugin | liteflow-rule-plugin（5 子模块） | 🚧 core 内已有雏形，S5 独立 |
| liteflow-script-plugin | liteflow-script-plugin（6 子模块） | 🚧 core 内已有 rhai/lua，S5 独立补齐 |
| liteflow-vernal | liteflow-spring / spring-boot-starter / solon | ⬜ S6 |
| liteflow-el-builder | builder/el（ELBus 链式 API） | ⬜ S3 |
| liteflow-agent | liteflow-ai-agent | ⬜ S7 |

硬性规范（用户指定，全阶段适用）：
1. 目录/文件名 snake_case；类型 PascalCase；方法 snake_case；参数命名与 Java 一致
2. Java 子包 → Rust 同名子目录；多层嵌套只要求最后一级完全对齐
3. 注释从 Java 复制并中文化，标注对应 Java 类与方法
4. jackson→serde；Spring Boot→axum；Quarkus→actix；Spring 容器→easy-4-rust/vernal；Agent→agentscope-rust
5. 一文件一对象；禁止 lib.rs/compat.rs 堆积对象；禁止 compat.rs 转发式引用
6. annotation/ 独立为 liteflow-derive（过程宏 crate）
7. 模板引擎速记：Tera≈FreeMarker、Handlebars≈Velocity、Askama≈编译期 JSP/Thymeleaf、maud≈Twirl/JSX
8. 功能语义对齐，实现方式 Rust 化

### S4 — liteflow-derive 过程宏（预估 2 个工作日当量）

**范围**：Java `annotation/` 包（AliasFor / LiteflowCmpDefine / LiteflowMethod / LiteflowRetry + util/）+ core/ 声明式组件体系（ComponentInitializer / FlowInitHook / proxy/）+ v2.16 的 @FallbackCmp 语义

**目标产物**：新 crate `liteflow-derive`（proc-macro）：
- `#[liteflow_component("id")]`：对应 @LiteflowComponent，自动实现 NodeComponent 注册样板
- `#[liteflow_method(...)]`：对应 @LiteflowMethod + LiteflowCmpDefine（声明式组件的方法标注 → 编译期生成组件）
- `#[liteflow_retry(n, for = [...])]`：对应 @LiteflowRetry，生成 retry_count()/is_retry_for() 实现
- `#[fallback_cmp("id")]`：对应 @FallbackCmp（v2.16）
- `#[alias_for]`：宏内部属性转发（对应 AliasFor，过程宏内部机制）

**实施步骤**：
1. cargo new liteflow-derive（proc-macro = true），workspace members 追加；syn/quote 依赖
2. 先 component 宏（最小可用），再 method/cmp_define（声明式组件全语义），最后 retry/fallback
3. trybuild 编译期负例测试（标注位置错误、参数缺失）；core 侧 decl_component.rs 对接
4. core/proxy：Java 用 JDK 动态代理实现声明式组件调用 → Rust 由 derive 宏直接生成调用代码（注释记录该架构差异）

**验收**：derive 宏复刻 decl_component 现有测试全部改为宏写法后仍绿；trybuild ≥4 负例；总测试 ≥140

## 五、工程规范与流程保障（全阶段强制）

### 测试门槛
- 每阶段完成时：既有测试必须全绿（只增不减）；新增语义必须带测试
- `cargo check --all-features` 通过、0 新增 warning
- 提交前必跑：`CARGO_TARGET_DIR=/tmp/lf-target cargo test --workspace`

### 推送流程（血泪教训，强制执行）
1. 推送内容**必须从磁盘读取**，禁止凭记忆内联（已发生 3 次转录走样）
2. 每批推送后**强制 git blob SHA 校验**（本地 `sha1("blob "+len+\0+bytes)` vs 远端回读），不匹配立即重推
3. 全部推送后克隆 dev 整库 `diff -r`，exit 0 才算完成
4. Cargo.lock 不推（库项目惯例）；.codegraph/ 不入库

### 并行策略教训
- **禁止在 $HOME 建 git worktree**（沙箱周期清空 $HOME，已摧毁过 4 个并行 worktree）
- 多子任务默认在主目录 `/mnt/agents/output/liteflow-rust` **串行**执行
- 确需并行时：文件所有权必须严格不相交，worktree 建在 /mnt 下

### 环境灾难恢复
- 工具链被清：`bash /mnt/agents/restore-rust.sh`（rsproxy 镜像，约 75 秒）
- protoc 被清：重新下载 protoc-25.6 到 /tmp/protoc-dist（etcd feature 编译需要）
- git 网络错误：`git config --global http.version HTTP/1.1`
- /tmp 会周期清空：CARGO_TARGET_DIR 在 /tmp 仅为提速，丢失无害（重建即可）
