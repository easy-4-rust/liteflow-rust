# LiteFlow → liteflow-rust 对象名称一致性检查

> 检查日期：2026-07-29
> Java 基线：LiteFlow v2.16.0
> 说明：本报告检查“对象是否按约定落位和命名”，不等价于功能语义已完成。

## 1. 检查规则

1. Java 顶级类、接口、枚举、record 各对应一个真实 `.rs` 文件。
2. Java 类名转换为 snake_case 文件名；Rust 主类型保留 PascalCase 对象身份。
3. Java 子包对应 Rust 同名目录；多层嵌套至少对齐最后一级。
4. Java 同简单类名依靠包路径区分，例如 Boot 3、Boot 4、Solon 的
   `LiteflowProperty` 不是重复对象。
5. `mod.rs`/`lib.rs` 只声明和重导出；内部类、伴随 Builder、类型别名可以与主对象
   同文件，但必须在对象表中说明。
6. Java 生态专有对象不能直接删除：必须标成“Java 专有 + Rust 等价语义入口”或
   “尚未迁移”，并有测试或边界说明。

对象待逐项语义裁决**，而不是“500/500 名称一致”。

## 4. JVM 专有脚本对象（15）

这些对象当前没有同名 Rust 文件，不得用“已有 Lua/Python/JS”直接计为对象完成。

| Java 模块 | Java 对象 |
|---|---|
| `liteflow-script-java` | `JaninoScriptBody`、`JaninoCommonScriptBody`、`JaninoBooleanScriptBody`、`JaninoSwitchScriptBody`、`JaninoForScriptBody`、`JavaExecutor` |
| `liteflow-script-javax` | `ScriptBody`、`CommonScriptBody`、`BooleanScriptBody`、`SwitchScriptBody`、`ForScriptBody`、`JavaxExecutor`、`JavaxSettingMapKey` |
| `liteflow-script-javax-pro` | `JavaxProExecutor`、`JavaxProSettingMapKey` |

裁决原则：

1. Janino 的“运行期编译 Java 源码”和 JSR223 的“发现 JVM ScriptEngine”属于
   JVM 专有机制，可以标记 🚫。
2. 它们对 LiteFlow 暴露的公共语义——五类节点、参数绑定、ScriptBean、
   编译缓存、校验、卸载/重载和异常——必须映射到 Rust `ScriptExecutor` 及具体
   原生引擎，并建立差分测试。
3. 若为每个 Java 对象建立 Rust 对偶文件，文件必须包含真实适配逻辑；禁止空对象、
   alias 或统一转发到 `compat.rs` 充数。
4. 完成逐项裁决前，这 15 项保持 ⬜/🚫 待定，不计入名称一致完成数。

## 5. 路径与红线扫描

当前扫描结果：

| 检查 | 结果 | 结论 |
|---|---:|---|
| `src/` 以下非 snake_case `.rs` 路径 | 0 | ✅ |
| `compat.rs` | 0 | ✅ |
| `lib.rs`/`mod.rs` 中 `pub struct/enum/trait/type` | 0 | ✅ |
| 生产 `todo!`/`unimplemented!` | 0 | ✅ |
| 文本命中的 wildcard import | 20 | 均为生产文件内 `#[cfg(test)]` 测试模块的 `use super::*`；生产实现为 0 |
| Java core 对象唯一 basename | 304/304 | ✅ 仅证明结构 |
| Java 全工作区直接 basename | 472/500 | ⚠️ 见第 3、4 节 |

仓库 crate 目录使用 Cargo 生态常见的 kebab-case（如 `liteflow-core`），而 `src/`
内部目录、文件均为 snake_case。目标结构本身使用 kebab-case crate 名，因此本报告
将“目录一律 snake_case”解释为 Rust 模块源码目录；若要求 crate 目录也必须
snake_case，需要单独迁移 package/path 名称并评估发布兼容性。

## 6. 类型与来源注释抽查

已确认：

- 3 个 ReAct 主类型仍为正确 PascalCase，但文件名不满足当前词边界规则。
- `ELSQLException` 类型与 Java 一致，差异只在文件缩写拆分。
- `NacosParseHelper` 类型本身与 Java 不一致，不只是文件名问题。
- `ReActLoggingHook` 文件头 Java FQN 与真实 Java 包不一致。
- Spring/Vernal 8 项当前是“语义替换对象”，不是“同名 Java 对偶对象”。

后续必须用语法树或 rustdoc JSON 全量扫描每个公开主类型和 `/// 对应 Java:`
注释；单纯正则无法可靠区分内部类型、宏生成类型和 `#[cfg(test)]`。

## 8. 结论与修复顺序

当前名称检查 **未通过最终验收**，但核心 304 和 EL Builder 18 的结构基线已经稳定。

1. P0：修复 `NacosParserHelper` 和 3 个 ReAct 文件名/FQN。

成为批准例外、15 个 JVM 对象逐项记录等价入口，且所有红线持续为零。
